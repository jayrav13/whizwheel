## Chapter 74 — The central-registration friction: a serial merge pipeline, and the frontend's de-facto registry (2026-06-14)

Where the backend wave merged seven-at-once with no conflicts, the **frontend wave did the opposite** — and exposed a structural finding the assistant tracked carefully. Every new-build frontend PR touches the *same* shared files: the result-dispatch in `_result.html.erb`, the label maps and `field_labels_for` dispatch in `calculators_helper.rb`, and the catalog card in `home/index.html.erb` (and the regens collide on `application.css`). The assistant named the consequence plainly: *"every new-build FE PR edits the same 3 central-registration files … and the regens collide on `application.css`. So each merge invalidates the next branch's mergeability — I'll merge one, rebase/resolve the next against the new `main`, repeat. Reliable but one-at-a-time."* A **serial merge pipeline** — the precise opposite of the conflict-free parallel fan-out the no-central-registration rule (#3) guarantees the backend.

The assistant connected it directly to the contract: *"the frontend has **three de-facto central-registration points** … Every new-calc FE PR edits all three, so parallel FE builds *will* conflict on merge … This cuts against the 'no central registration — add a calculator by adding a file' principle that keeps the *backend* conflict-free."* It filed the finding as **#107** (proposing dynamic dispatch / per-calculator registration for the frontend). The pipeline ran exactly as predicted: #99 and #103 merged clean, then each subsequent PR had to merge `main` into its branch and **union-resolve additive conflicts** — handled in-domain by dispatched `frontend` resolver agents rather than risked as hand-merges. The fiddliest reconciliation was the **dual `money_display` helper**: Amortization defined one taking an already-rounded 2dp String from the envelope, Simple Interest defined one taking a BigDecimal; the resolver merged them into *"a single method that handles both inputs … '2dp, half-up, thousands-delimited.'"* The `field_labels_for` case statements likewise had to be *merged into one* with a `when` branch per calculator, not duplicated. Each resolution re-ran the suite to 100% single-process coverage and verified the main checkout stayed clean before pushing.

A second frontend-agent gap surfaced in the same stretch: **MMR (#102) shipped without a home-page card.** The vision review returned CHANGES-NEEDED — *"the page itself is fully BLEND-conformant, but the agent didn't add the MMR card to `home/index.html.erb`, so MMR has no discoverable link from the home grid."* The assistant filed it as **#108** (the frontend agent def needs an explicit "register the home card" step) and dispatched a frontend agent to both resolve MMR's conflicts and add the missing card. A `ci-monitor` diagnosis also explained why **Tip's #106 never fired CI**: its branch was `dirty` (conflicting with `main`), and *"GitHub Actions sometimes skips firing when a PR has merge conflicts with the base"* — so the same conflict-resolution step that the central-registration friction forced *also* re-armed its CI via the `synchronize` push, no separate trigger needed. **Agent/doc-driven? ✅** — every conflict resolution went through a dispatched frontend agent in its own worktree, and both structural gaps (central registration #107, home-card registration #108) were filed as agent-def-targeting issues rather than absorbed as orchestration toil.

The session filed a dense batch of findings here — **#107–#112** in one pass — covering frontend central-registration, the frontend-agent registration checklist (the MMR miss), integer-coercion vs `only_integer` (Tip/Amortization), non-numeric `:decimal` coercion (Percentage regen), the SimpleCov-in-parallel undercount, and two DESIGN conventions (financial color: interest shown green in the Amortization donut but coral in tables; and card-eyebrow `faint` vs green §2). The assistant framed this finding-pile as *"the experiment's real output"* — the build's durable value being the agent-layer lessons it surfaces, not the calculators alone.
