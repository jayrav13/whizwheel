### The first parallel multi-calculator build — staged in two waves

The assistant named a sequencing constraint the fan-out exposed for the first time: *"a frontend page's system test + screenshot renders **real** results, so it needs that calculator's backend math present. So I'm building in two waves — **BE first → merge → FE** — rather than all four at once."* This is a genuine structural finding about the build model — backend and frontend specs are independent to *author*, but a frontend agent's screenshot self-review (its own quality gate) needs the live calculator to render against, so the FE wave must follow the BE merge.

**Wave 1 (backend, parallel):** the two backend agents ran concurrently in their own worktrees — *"independent — 'add a calculator = add a file,' so no collision."* Both came back 100% line+branch, rubocop+brakeman clean (Ohms #57, BMI #58). With `ci-monitor` on each (per the agent-opened-PR rule firmed in Chapter 61), both reported green and merged clean — *"no collisions"* — landing `bmi.rb` + `ohms_law.rb` on `main` together (`44de6e8`). The iteration docs PR #56 merged first as low-risk independent docs (`573e81f`).

**Wave 2 (frontend, parallel):** the two FE agents ran off the updated tree. Ohms FE landed first (PR #60) — and its agent flagged the collision the user had predicted: it had touched **three shared files** (`_result.html.erb` dispatch branch, `home/index.html.erb` catalog card, `calculators_helper.rb` — including a `percentage_display`→`decimal_display` rename with a back-compat alias) and warned *"The BMI PR will likely touch the same three files — expect a trivial rebase to reconcile."* The assistant ran the real visual gate on #60 (UI-surface → view the changed/new shots), looked at all six affected shots against `DESIGN.md`, confirmed the math and the `GIVEN`/`SOLVED` text-badge accessibility, and merged it — *"so BMI rebases onto a main that already has Ohms."*

### Two real-world snags worth recording

**(1) A `gh` hang that looked like a stuck agent.** The user, watching the BMI FE agent's slow progress, judged it stuck: *"Based on the progress of the BMI frontend, I think it's stuck. Can you kill and re-start it? … it's genuinely stuck on fetching the issue using `gh`."* The assistant began prepping the restart — but checked first, and found the agent had simply *finished*: *"the BMI FE agent **wasn't stuck — it just finished** (it's a heavy build; ~16 min vs Ohms' ~9.5). It opened **PR #62** … So **no kill/restart needed** — I'm glad I checked before terminating, that would've thrown away a completed 16-minute build."* Checking before killing saved the work; the `gh` slowness was real but had completed.

**(2) `bin/dev`'s CSS watcher tore down the backgrounded server.** Asked to spin up the app, the assistant ran `bin/dev` and saw it exit code 0 instead of staying up. Diagnosis: *"the server booted fine (Puma served a 200 on `/`), but `tailwindcss:watch` exited immediately in the non-interactive background shell, and foreman tears everything down when any process exits."* The fix was to build the CSS once (`tailwindcss:build`) and run a plain `rails server` with no watcher — *"you're trying the app, not editing styles."* The server then served `/`, `/calculators/percentage`, and `/calculators/ohms_law` at 200 for the user to try.

The **BMI #62 collision** was resolved exactly as predicted — by an **additive rebase** (a dispatched frontend agent reconciled the three shared files, keeping *both* result-branches, *all three* home tiles, and `decimal_display` defined exactly once), force-pushed to trigger a fresh CI run, then visual-gated (the BMI pages plus two *surprise* sha-changed shots that turned out benign — shared-partial re-renders, *"exactly the 'non-UI-looking change touched a shared file → screenshot moved → look at it' scenario the gate exists for"*) and merged. **Agent-driven? ✅** — every calculator and page was an agent's from-spec output; the scaffolding was the only hand-built plumbing, untouched.
