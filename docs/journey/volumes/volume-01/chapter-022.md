## Chapter 22 — The dogfood: an agent reads DESIGN.md and the BLEND taste rides in (2026-06-13)

This is the chapter the whole frontend arc was built to produce: **the first test of whether visual taste rides into agent-written code through a doc.** With the toolchain and `DESIGN.md` in place, the assistant dispatched the freshly-written frontend agent (read-and-adopt, since it isn't a registered type until a session reload) to restyle `home/index` (signed-in/out) and `sessions/new` (with the Chapter-14 flash) — the first BLEND reference implementation.

**Verify, don't trust the report.** The agent reported done and green; the assistant ran the same independent-review discipline the foundation established (*"not trusting the report"*). Scope first: *"only `app/assets`, `app/views`, `test/` touched; no backend."* Then a four-axis read — tokens (*"all 11 colors + font in `@theme`; every color in markup uses a token utility … no hard-coded hex"*), a11y (labels on every field, `focus-visible:ring-accent`, `role="alert"`/`role="status"`, semantic landmarks), and tests (the 4 integration tests assert the real states, including the failed-login `[role=alert]`). The independent gate run confirmed *"26 runs / 85 assertions / 0 failures, 100% line+branch, rubocop clean. The report holds up."*

**The guardrail caught something real — and judgment, not blind agreement, decided what to do.** The very guardrail authored in Chapter 21 fired on the agent's own output:

> "**One real finding (per our own guardrail):** the card/button/eyebrow/input clusters repeat ≥3× across the three views, and radii (`rounded-[18px]/[13px]/[11px]`) + the card shadow are uncommented arbitrary values. DESIGN.md §5 says extract those into `@apply` classes / `@theme` radii. The agent *deliberately* left them inline for a 'transparent first pass' and flagged it. I'm going to **accept this pass and batch that extraction with your visual feedback** — it's a maintainability refinement (identical pixels), and doing it *once*, informed by any tweaks you want from the screenshots, beats doing it twice."

So the agent *self-flagged* the arbitrary values it left inline, and the reviewer chose to defer-with-reason — the same receiving-review discipline seen across the foundation chapters, now applied to the agent's own UI. (This deferred extraction becomes issue #15 — see Chapter 25.)

**Live, with the tokens actually compiled.** The assistant stood up the app for the user's visual gate (Task 6) and verified live: anonymous home and login both HTTP 200, and *"Compiled CSS … 16 KB — contains `#ef6c4d` (coral) + `#fdf8f3` (cream), so the `@theme` tokens compiled into real utilities and are being served."* It surfaced a foreman quirk honestly — the `css` watcher exits immediately when *the assistant* backgrounds foreman in a non-TTY, so it ran Puma directly for the review (*"in your own terminal `bin/dev` works normally"*). It then handed the four states to the user with the experiment's real question: *"This is the experiment's real question, so react honestly: **does this meet your expectations?**"*

**The result, in the assistant's words.** The user replied with five screenshots of every changed UI. The assistant's read of them was the headline experiment data point of the arc:

> "This is a genuinely strong experiment result: the frontend agent, reading only `DESIGN.md`, produced UI that faithfully matches the approved BLEND taste — cream canvas, the green brand dot and eyebrows, the sharp sweeping headlines, the coral primary actions, the soft cards, and the coral alert (the Chapter-14 flash, now styled). All four states are correct, including the nav flipping to 'Signed in as demo' + outline Sign out. **Visual taste rode in through the doc.**"

This closes the symmetry the experiment proposed in Chapter 5 and extended in Chapter 20: as the conventions doc carried the user's *engineering* style into agent-written foundation code (Chapters 13–17), `DESIGN.md` carried the user's *visual* taste into agent-written UI — an agent that never saw the three rounds of mockup-narrowing nonetheless produced the settled BLEND look. The PR shipped: **PR #8 (`Closes #7`), CI green on all five jobs, merged on the user's nod** as merge commit `911c460`, issue #7 closed, branch deleted.

**Agent-driven?** ✅ The UI was written entirely by the frontend agent reading `DESIGN.md`; the only main-thread actions were the independent review, the live verification, and the git mechanics. The single deferred item (component extraction) was the agent's own self-flag, handled through the process. This is the clearest evidence yet that *visual* taste — the domain the founding "describe in words" method covered least well (Chapter 20) — can be carried into agent output through a doc, even though the taste itself was settled by *looking*, not writing.
