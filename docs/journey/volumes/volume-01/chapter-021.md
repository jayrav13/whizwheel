## Chapter 21 — The frontend toolchain lands: Tailwind installed, the build step reversed for real, DESIGN.md + the agent written (2026-06-13)

This chapter opens the session that took Chapter 20's *design* (the BLEND spec, the Tailwind decision, the lane split) and **built it end-to-end** — the frontend agent's first real existence, exercised on the stubbed login/home pages. It is a single long arc; this chapter covers the toolchain install and the artifacts the main thread owned per the Chapter-20 lane split (Tailwind, `DESIGN.md`, the agent def, the CLAUDE.md edits). The chapters that follow cover the dogfood, the verification tooling, the testing canon, and the first real iteration.

**From spec to plan, grounded not guessed.** With the Chapter-20 spec approved (*"looks good, continue"*), the assistant moved to an implementation plan via the writing-plans skill — but grounded the CI/tooling details first rather than assuming them: *"Two facts that shape the plan: CI renders the layout in the `test` job too, so once we add the Tailwind `<link>`, **every** test needs `tailwind.css` built first (Propshaft raises on a missing asset) — so CI gets an explicit build step in both jobs. And since the login/home pages have no JS yet, **integration tests** (render + states, no browser) are the right, cheaper tool — system tests stay reserved for when Stimulus interactions appear."* The plan landed as `e9eaad5`. The assistant described it as **hybrid by design**: Tasks 0–4 (branch, Tailwind, `DESIGN.md`, CLAUDE.md, the agent def) run inline in the main thread per the Chapter-20 lane split; Task 5 — *"the actual experiment"* — dispatches the freshly-written frontend agent; Tasks 6–7 keep the two human gates (the user judges the screenshots; the user gives the merge say-so).

**The flexibility question — and the guardrail it produced.** The user asked a sharp question that re-opened the Tailwind choice on its merits: *"Am I wrong in saying that TailwindCSS that'll offer us the best long term flexibility?"* The assistant pushed back precisely — flexibility is the one axis where Tailwind *isn't* the winner — and reframed the real reason:

> "Strictly on raw flexibility, plain CSS wins. … But for *this* project, flexibility isn't the axis that matters most … **Tailwind isn't the most *flexible*, it's the most *leverage*** — best velocity + consistency + agent-friendliness, which for an agent-built, consistency-critical, many-page app is the better bet."

The argument that made it specific to *this* method: *"Tailwind is the most-represented CSS approach in LLM training data — agents write idiomatic, *consistent* Tailwind far more reliably than they invent and adhere to a bespoke CSS architecture. For an **agent-authored** UI across 191 pages, that consistency-by-default is worth more than raw expressiveness."* The assistant then named the real risk and turned it into a durable artifact — exactly the experiment's "encode the lesson in the agent" move:

> "The one real risk is **arbitrary-value drift** — the agent reaching for `text-[#ef6c4d]` / `mt-[37px]` and quietly eroding the token system. … I'll add a guardrail to `DESIGN.md` and the frontend agent def — *'prefer `@theme` tokens; treat arbitrary `[...]` values as a smell to justify.'*"

The user accepted in one line — *"Yep fold in that guardrail and start"* — and the **token guardrail** became part of both `DESIGN.md` and the agent definition.

**The build step reversed, for real.** This is where Chapter 20's celebrated-property trade became concrete. The assistant installed **Tailwind v4** (`tailwindcss-ruby 4.3.0`, the standalone binary — no Node) via the `tailwindcss-rails` installer, then inspected what it generated rather than trusting it: the installer *"did not add the `tailwind` stylesheet link to the layout (its gsub didn't match our customized `<body>` with the flash loop)"* — so it wired the `<link>` in by hand — and it **kept** the generated rails-omakase `bin/dev` and `Procfile.dev` (foreman: `web` + a `css` watcher). The suite stayed *"22 green, **100% line + branch coverage**"* with the Tailwind link live, and the assistant added an **explicit CI build step in both test jobs** for determinism (Propshaft raises on a missing asset). Committed as `b3f0be6`. This is the moment CLAUDE.md's hard-won Chapter-17 *"no Procfile, no foreman"* property was deliberately undone — the trade the user chose in Chapter 20, now real in the repo.

**`DESIGN.md`, CLAUDE.md, and the agent def.** The assistant authored **`docs/DESIGN.md`** — the full BLEND system plus the arbitrary-value guardrail (`acad201`) — then made four targeted CLAUDE.md edits (`458ea3f`): added `DESIGN.md` to "Read these first," **rewrote "Starting the app"** to the foreman/Tailwind reality (`bin/dev` now runs foreman from `Procfile.dev`; the built CSS is gitignored and CI builds it with `tailwindcss:build`), and added the frontend agent to the roster. Finally it wrote **`.claude/agents/frontend.md`** (`98f2acf`) — the agent now exists, owning `app/views`, `app/helpers`, `app/assets` (theme/tokens), and Stimulus controllers, reading `DESIGN.md` first per the pm-launch-protocol model, and barred from calculator math, models, controller business logic, migrations, and routes.

A small process moment worth recording: the assistant tried to push the 3 local-only docs commits (spec, ch20 journal, plan) to `main` so the eventual PR diff would be *"just the #7 implementation"* — and the push was **denied** by the user's own no-direct-push-to-`main` rule. The assistant noted it correctly: *"Denied — and correctly: that's your own no-direct-push-to-`main` rule doing its job."* The docs commits simply rode along in the PR diff and reconciled at merge.

**Agent-driven?** ✅ for the artifacts that carry intent forward — `DESIGN.md`, the frontend agent def, the CLAUDE.md edits, and the token guardrail were all authored by the main thread per the Chapter-20 lane split (the same pattern as the foundation's toolchain: infra/docs are main-thread, the *product* is the agent's). The Tailwind install itself is honestly an infra hand-edit (Gemfile + generator + a hand-wired layout link + CI build steps), but it is outside the calculator/UI build path the agents own — and it is the deliberate reversal of a journey-celebrated property, chosen by the user with the cost surfaced first (Chapter 20).
