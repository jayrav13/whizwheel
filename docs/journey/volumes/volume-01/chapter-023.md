## Chapter 23 — Closing the visual loop: headless screenshots the session-side Claude can actually see (2026-06-13)

The user, having just judged the dogfood by hand-capturing five screenshots, asked the question that would reshape the verification design: *"What options do we have to automate even this process such that you can view the results headlessly for verification?"* This chapter is the answer, built across two PRs (#9, #13), and it surfaces a genuinely load-bearing insight about *where vision lives* in the agent stack.

**Prove the concept, then pick the tool.** The assistant first proved it could see a headless render at all — capturing the live home page with `chrome --headless --screenshot` and looking at it directly: *"I can now verify the actual pixels, not just test assertions or your screenshots."* But it named the catch immediately — that raw call only works for *plain GET pages*; the signed-in and failed-login states need a driver. It laid out three options (Capybara+Selenium, already bundled; Cuprite/Ferrum; a Chrome CLI helper) and recommended **A — Selenium**, *"with full-page capture,"* because it reuses the Rails-default stack, covers every state, turns the dormant CI `system-test` job into a real gate, and — the agent-first part — lets it *"wire 'capture + self-review screenshots against `DESIGN.md`' into the frontend agent's quality bar, so the agent visually checks its own work before a human ever looks."* The user chose A + full-page + ship #7 first.

**#9 — the screenshot pipeline, with the coverage-gate subtlety handled.** The assistant built a Capybara/Selenium system test that drives every state and saves **full-page** PNGs (resizing the window to document height — *"yes, we can do full-page with Selenium, no extra gem"*). It pre-empted a real CI trap: the `system-test` job runs separately from the unit `test` job, so if the system tests load the SimpleCov-gated helper, *"the 100%-coverage gate would fire on the system run (which alone can't hit 100%) and fail CI."* The fix: **make the gate skip when `NO_COVERAGE` is set, and set it only for the system run.** Locally, 4 system tests passed and the captures matched the user's manual screenshots; the assistant viewed them itself and quieted a cosmetic *"thin blue line"* (Turbo's transient progress bar caught mid-fade). It wired the self-review step into `frontend.md`. PR #10 went green on all five jobs — *"headless Chrome in CI for the first time"* — with the `NO_COVERAGE` guard working exactly as intended.

**The insight that defined the design: where vision lives.** The user pushed on a deeper question after viewing the CI artifacts himself: *"What specific value does it generate in GH Actions? What would be considered a failure? There's no Claude integration in GH actions itself as I understand it correctly."* The assistant split two conflated things — *"The system **test** is the real CI gate"* (its value is the assertions; structure/behavior regression), while *"The uploaded PNGs have **no automated value in CI itself**"* (their value is forensic/audit: a human or session-side Claude downloads them later to *see*). It conceded the user's premise — nothing in GH Actions *looks* at the pixels — and named what CI can and cannot catch: *"CI checks **structure and behavior**, never **appearance**. … **the font silently falling back** all pass CI as long as the asserted text is present."* (That last clause is the thread that becomes Chapter 24.)

The user then proposed the design that stuck: *"can we add a step on our end where you (Claude) pulls the artifacts that we know are deterministically generated by the CI/CD while we're monitoring and review the screenshots generated?"* The assistant agreed it was *"cleaner than trying to run Claude inside GH Actions"* and named the constraint that decided *where* the step lives:

> "The key constraint that answers your question: **`ci-monitor` is Bash-only — it has no vision.** It can *download* artifacts but literally cannot *look* at them. So the *seeing* can't live there."

The clean division: **ci-monitor watches/reports status (and could pre-download the artifact); the main thread pulls `ui-screenshots` and reviews against `DESIGN.md`; a vision review subagent is the scale-up** (to keep image tokens out of the main context once many calculator pages get reviewed per PR). The assistant proved the loop end-to-end before codifying it — *"`gh run download` → `Read` → review, all session-side, fully deterministic."*

**#13 — the visual gate, codified.** The assistant built **`bin/ci-screenshots <pr|run>`** (mirroring `bin/ci-watch`: resolve the PR's latest run, download `ui-screenshots`, print the path) and codified the gate in CLAUDE.md's CI/CD section + cross-linked it from `ARCHITECTURE.md §11`. PR #13 (`Closes #12`) went green and merged (`dd06958`). Two things worth recording from #13: the assistant **ran the visual gate on #13 itself** even though it was a bash+docs PR — *"it's cheap reassurance"* — confirming the render was identical to #10 (no incidental regression), which *"confirms the scoping: a non-UI PR's screenshots are unchanged."* And then the user broadened the policy:

The user's instruction, after #13 merged, was to pull screenshots on *every* CI run, not just UI PRs. The assistant agreed — *"it's cheap and the Linux render is a useful cross-platform check regardless"* — and committed the policy tweak (`3711cc1`): the visual gate now runs on **every** PR, *"regardless of whether the diff looks UI-related,"* because the CI/Linux render is a proxy for "what a non-Mac visitor sees" that can catch regressions a code diff hides.

**Agent-driven?** ✅ for the agent-facing pieces — the screenshot self-review step wired into `frontend.md`, and the visual gate codified into the inherited contract (CLAUDE.md + §11). The pipeline code (`bin/ci-screenshots`, the system-test base class, the `NO_COVERAGE` split, CI job edits) is verification *tooling* — main-thread infra work, like `bin/ci-watch` before it, outside the product-build path. The design's load-bearing realization — *vision lives in the session, not in CI or the Bash-only ci-monitor* — is encoded as a convention, not improvised.
