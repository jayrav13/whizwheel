## Chapter 101 — The keystone delivered: the registry built, two new agents envisioned, and #107 dispatched (2026-06-14)

This is the chapter where the architecture the operator chose in Chapter 94 — a DB-backed calculator registry, against the agent's recommendation and the old rule #3 — became running machinery, and where the operator's vision expanded the agent roster by two. It is also the **first chapter written under the new volume structure** (Chapter 99), opening Volume 05.

**The machinery (PR #162, `Closes #153`).** Gated correctly on the PM finishing the #153 fold so the spec was complete, the backend agent built the registry end to end: a `calculators` table (a table-only migration, no ingest baked into it — the Chapter 95 `structure.sql` lesson held), a `Calculator` model with `.active`/`.deprecated` scopes and a `deprecated_at` column for **deprecate-never-delete**, and the ingest itself split into testable `lib` services — `Registry::InventoryParser` (header-name parsing, *"reorder-robust"*) and `Registry::Ingest` (*"idempotent upsert, `Base.lookup` reconciliation, loud drift warning, deprecate-not-delete + reinstate"*) — plus a `calculators:ingest` rake task, a `db/seeds.rb` hook for fresh DBs, and `test/fixtures/calculators.yml` for the test DB (the fixtures-for-tests / seeds-for-fresh split the contract demanded). It reported **558 runs, 100% line + branch coverage**, rubocop and brakeman clean, and honored the per-issue scope precisely: *"only the 8 built (slugged) calculators are ingested; the full 191-row catalog ingest is left to #122."* The operator merged it — *"merge 161 and 162 when complete, make db agent update, and then do 107 FE work"* — landing the registry live on `main` (`d2ffa13`). The keystone the assistant had recommended against building this way now existed, built faithfully to the operator's chosen design.

**`database-agent` extended (PR #164).** Per the Chapter 96 ownership split, the assistant extended the `database-agent` definition from pure read-only inspector to *operate* the one sanctioned mutation: *"carving out the one sanctioned ingest mutation"* — it can now run `bin/rails calculators:ingest` and report drift, while remaining a general read-only inspector for everything else. The assistant also updated CLAUDE.md's registry-ownership line *"to reflect the def is now extended (not 'being extended')."*

**#107 FE work dispatched — the payoff, kept frontend-only.** With the registry live, the assistant scoped the keystone deliberately to the frontend lane: *"For #107 I'm keeping it **frontend-only**: the catalog will read the registry through a thin view-helper (`Calculator.active`), which is a read-only display query in the FE lane — no controller/model changes needed, matching your '107 FE work.'"* It dispatched the frontend agent to build the registry-driven catalog + convention-based result dispatch + the per-calculator helper split — the three shared files Chapter 93 had sized — and noted this PR *moves pixels*, so the **UI-surface visual gate** (actual screenshot review) applies, unlike the docs PRs that had been clearing on the #87 file-evidence basis all session.

**The roster expands by two, from the operator's vision.** While the registry build cooked, two larger agent-design ideas crystallized into filed-not-built issues. The first, **#160 `quality-assurance-agent`**, came from the operator's instinct to consolidate the pre-merge gate; the assistant endorsed the unifying concept but added a sharp nuance and named a concrete win: *"the visual gate today runs in the main thread ... which means **image tokens land in my context every PR**. That's literally the problem #93 was filed to fix. A QA agent that owns CI + DB + screenshots returns **one PASS/FAIL verdict with all the heavy tokens ... kept out of the main thread.**"* Its one correction was to *not* collapse the general-purpose inspector into it: *"`ci-monitor` folds in cleanly ... `database-agent` has a life beyond gating ... Don't dissolve that."* So #160 absorbs `ci-monitor`, folds in #93 (vision review) and #127 (DB-persistence check), depends on #87/#61 (the gate-reliability mechanisms it relies on), and keeps `database-agent` standalone. The second, **#163 `github-agent`** — *"issues + labels + dedupe + PR creation + branch rebasing"* — was filed distinct from #160's QA gate, the assistant noting the small irony unprompted: *"the irony of filing 'an agent to manage issues' as an issue is noted."*
