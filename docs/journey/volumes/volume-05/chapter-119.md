## Chapter 119 — A stats page "outside the iteration pattern": the first admin area, scoped by the brainstorming skill (2026-06-15)

This chapter opens a new development thread that is notable precisely for what it is *not* — not iteration-0007, not a calculator, not pinned to a tagged agent set. In a fresh session, immediately after the iteration-0006 close (Chapter 118), the operator asked for a one-off feature, built directly in the main thread:

> **"Can we knock out a quick stats page (overall admin history) for this app? Very modular to the rest of the app, use relevant agents as needed but otherwise build outside the iteration pattern in main thread here"**

That instruction is the chapter's frame and worth dwelling on. The experiment's spine is the *iteration* — open/build/evaluate/harvest/journal/close, pinned at an agent SHA, propagated by the regen sweep. The operator deliberately stepped *out* of that machinery for a small, self-contained piece of infrastructure: still using the build agents ("use relevant agents as needed"), but orchestrated ad-hoc in the main thread rather than run as a scoped iteration. It is the first time the project has consciously drawn the line between *iteration work* (the calculator catalog, the thing the experiment measures) and *modular app infrastructure* (a feature the app needs that doesn't belong in the regen set). The stats page reads logs and renders a dashboard — it is not a calculator, so erasing-and-regenerating it from a spec would be meaningless; it lives outside the sweep by its nature.

**The skill ran before any code — scope nailed first.** Rather than start building, the orchestrator invoked the **brainstorming skill** (newly available from the `pr-review-toolkit`/superpowers plugin committed in #218 the session before): *"I'll start by invoking the brainstorming skill to nail down scope before building — this is creative/feature work, and getting the spec right up front is exactly what keeps it 'quick.'"* This is a small but real process note: the operator's word was *"quick,"* and the orchestrator's read was that for a quick build the leverage is in a tight spec up front, not in skipping the spec. It launched a recon subagent to map the existing logging/auth/admin/view infrastructure in parallel with asking scoping questions — staying ahead of the airplane even on a one-off.

**The scope the operator chose — four metric groups + a chart.** Through the brainstorming dialogue the scope settled on an *overall* calculation-history dashboard with four metric groups, plus a trend chart:
- **Volume** — counts for today / 7d / 30d / all-time, plus a 30-day daily series (the chart's data, zero-filled for empty days).
- **Top calculators** — group-by-calculator, count desc, top 10.
- **Anonymous vs attributed** — the null-vs-present `user_id` split, plus top users by activity.
- **Recent feed** — the latest 50 rows (calculator, who/anon, when, short input/result summary).

The trend renders as a **dependency-free inline-SVG bar chart** driven by a small Stimulus controller — a deliberate choice to honor the repo's standing no-Node/importmap constraint rather than reach for a charting library. (The same instinct that has governed the whole frontend toolchain since Chapter 21.)

**The first admin-only area — and the pattern it establishes.** The load-bearing architectural decision is that this is the *first* admin-gated surface in the app, so it has to establish the reusable pattern. The design: a new `admin` namespace, an `Admin::BaseController` running a `require_admin!` before_action added to the existing `Authentication` concern, and `Admin::StatsController < Admin::BaseController` as the only action for now. The gate's behavior was chosen with intent — **404 for non-admins, not a redirect** — and the orchestrator stated the reasoning explicitly: *"otherwise 404 (not redirect — don't reveal the route exists)."* Hiding the existence of the route from anonymous and logged-in-non-admin users alike is a security posture decision, not just an access-control one, and it is now the template every future admin page inherits. An admin-only **"Admin"** nav link (shown when `current_user&.admin?`) rounds out the surface.

**The data layer — an isolated, fully-testable query object.** Faithful to the architecture's purity discipline (the same principle that makes the math layer 100%-coverable), the data lives in a `CalculationStats` PORO — *"isolated PORO, 100%-coverage-testable via fixtures"* — that reads the existing `calculation_logs` view and **always filters soft-deleted rows** (`deleted_at IS NULL`), honoring rule #4. Its methods are the documented surface: `volume`, `daily_series(days: 30)` (zero-filled, chart-ready), `top_calculators`, `attribution`, `top_users`, `recent`. Keeping the query logic in a plain object — not buried in the controller — is what lets it be unit-tested to the coverage gate against fixtures, the same reasoning the project applies everywhere DB-touching logic could otherwise resist testing.

**Delivery — two PRs, backend-first, decoupled by a contract.** The operator locked the shape: *"two PRs (backend first), 404 for non-admins."* Backend lands first (route + admin gate + the `CalculationStats` query object + controller + tests), then frontend (the ERB view + SVG chart + admin nav link + tests). The seam between them is a single contract — the controller assigns one `@stats` object (the `CalculationStats` instance) and the view calls only its documented methods. The orchestrator named why that seam matters: *"That's the seam that lets the two agents work against a stable interface."* It is the same backend⇄frontend JSON-envelope discipline the calculators use, transposed to a server-rendered page — the two build agents work in parallel against a fixed interface rather than serially against each other's internals.

**A process adaptation worth recording — the skill's default bent to the repo's convention.** The brainstorming skill's checklist prescribes writing the design doc to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`. The orchestrator did *not* follow that default, and said why — the skill itself defers to project patterns, and this repo's native spec convention is the GitHub issue body (`spec:v1`):

> **"One adaptation on the spec home: this repo's spec convention is GitHub issue bodies (`spec:v1`), not `docs/superpowers/specs/` — and the skill defers to existing project patterns. So I'll write the spec, file a `backend` + `frontend` issue carrying it (via `github-agent`, which dedupes/labels), and the PRs close them."**

This is a clean example of an external skill being *absorbed into* the repo's established conventions rather than imposing its own — the spec got the rigor the skill demands (a written, self-reviewed spec the operator approved before any code), but lands in the repo's own home (two `engineering`-labeled GitHub issues, one per layer) so the existing Issue → Branch → PR → `Closes #N` machinery carries it. The orchestrator ran the skill's spec self-review inline (*"no placeholders, the two layers are consistent, scope is the four metrics + chart you chose, and the 404 behavior is explicit"*) and put the full spec to the operator, who approved: *"Good to go"*.

**Where the thread stands at journal time.** With the spec approved, the orchestrator dispatched `github-agent` to file the two issues (`backend` + `frontend`, both `engineering`-labeled) — explicitly waiting on the returned issue numbers before firing the backend build, since it needs the number for the branch and the `Closes #N`: *"The backend build is the next thing to fire the moment the issue numbers land. I'll dispatch it then."* The historian was fired in the background to journal the kickoff (*"📝 journaling that in the background"*) — this chapter — while the issue-filing and the backend build proceed.

**Agent/doc-driven? — agents used, nothing codified yet.** No agent definition or doc changed in this kickoff; the work is *built by* the existing agents (recon subagent, `github-agent`, then the `backend` and `frontend` build agents), orchestrated by hand in the main thread per the operator's instruction. The durable record here is the *shape* of an out-of-iteration feature build: scoped by the brainstorming skill but homed in the repo's own `spec:v1`/issue convention, establishing the app's first admin area (namespace + `require_admin!` 404 gate as the reusable pattern), with the data isolated in a coverage-testable query object and delivery split into a backend-first, contract-decoupled pair of PRs. Whether the two build agents reproduce the BLEND/architecture conventions correctly on a *server-rendered admin page* — a surface they were not specifically written for — is the open question this thread will answer in the chapters that follow.
