## Chapter 112 — The backend fan-out: a razor's-edge spec defect, a registry-coordination collision, a namespace clash, two agent deaths — and 14 calculators live (2026-06-15)

This is the demanding chapter — the iteration-0006 backend wave, six parallel builds, where the experiment paid off repeatedly: the build agents' "refuse to guess / hand back" discipline and the QA gate caught a spec defect, a whole registry-coordination design gap, and a namespace collision *before any of it shipped*, and each became a durable agent/process fix. The orchestrator named the throughline mid-flight: *"This has been a genuinely demanding iteration to orchestrate — six parallel builds, a spec defect, a registry-coordination redesign, two agent deaths — and it's now lined up to land cleanly."*

**The fan-out: five in parallel, Mortgage held.** With the twelve issues filed, the orchestrator launched the backend builds — *"Loan + the 4 independents (Compound Interest, Std Dev, Right Triangle, Date) in parallel (backend-first), holding Mortgage #186 until Loan's backend PR is up so it builds on the proven loan core."* The hold is the Chapter 107 sequencing rationale made operational: Loan is the cluster primitive Mortgage extends, so Mortgage waits for Loan's PR to exist.

**Catch #1 — Loan stopped on an internally-inconsistent spec.** The Loan backend agent built `loan.rb` (all three modes), verified five of six reference cases exactly — *and stopped*, refusing to commit, because one pinned reference could not be reproduced without contradicting the spec's own authoritative rule. The agent reported it precisely: in `term` mode, the case `25000, 471.78 @ 5% → term_months = 60` gives two conflicting instructions — the formula + *"Round n up to the next whole month"* rule, versus the pinned value of 60. The actual math, *"computed at full BigDecimal precision via `BigMath.log`, 40 digits — not float error,"* lands `raw n = 60.000121495…` — *"genuinely above 60"* — so `ceil` correctly produces **61**, not the pinned 60. The cause: `471.78` is the exact 60-month payment (`471.7794…`) rounded *up*, which makes the term land a hair over a clean 60. The agent even caught that the spec's worked narrative was self-inconsistent: *"The spec's worked anchor narrative is itself wrong: it states 'n = 59.99… → rounded up to 60,' but the true raw value is 60.0001…, not 59.99."* It laid out three resolution options, recommended re-pinning, and was explicit about its boundary: *"re-pinning a reference value is a PM/spec decision, not mine to make."*

The orchestrator endorsed both the stop and the robust fix: *"The Loan backend agent did exactly the right thing — it stopped rather than guessed on a genuine spec inconsistency. This is the contract working as intended."* Rather than re-pin to 61 (still sensitive to 5th-decimal precision), it routed the PM to *"choose a `term`-mode reference whose raw `n` is unambiguously fractional ... so ceil is well-defined — keeping the standard 'round up to whole month' rule."* The PM re-pinned to `25000, 600.00 @ 5%`, which gives `raw n = 45.86083…` — *"≈ 0.14 below 46 — unambiguously fractional, no precision razor's edge"* → `ceil` → 46 (total_interest 2516.64, total_paid 27516.64, reconciliation verified). The ceil *rule* was kept; only the example changed. The Loan agent then resumed (the `loan.rb` was already built — *"this is finish-the-job"*) and opened `PR #201`. The orchestrator banked the lesson: *"don't pin reference values at integer razor's edges."*

**Catch #2 — a registry-coordination collision (rule #3 surfacing under fan-out).** As the backend PRs opened, a systemic problem emerged that *every* new calculator would hit. Right Triangle (`PR #196`) and Standard Deviation (`PR #197`) both came back at 100% coverage but red on the same test: `Registry::IngestTest` fails because the new calculator's row in `docs/INVENTORY.md` lacks its `Slug` + `Description`, so a *built class with no complete row registers as drift*. The orchestrator named it: *"a systemic blocker that will hit every new calculator ... all six backend PRs will go red until INVENTORY.md is backfilled."* But there was a second, sharper edge. Compound Interest (`PR #199`) had *crossed the seam* — it edited `docs/INVENTORY.md` itself *and* bumped a shared count assertion (`test/tasks/calculators_test.rb` hard-coded `upserted=8` / `active.count == 8`) — which would conflict with the PM's centralized backfill *and* with every other calc that bumps the same count. The orchestrator diagnosed the root cause: *"A shared hand-asserted calculator count that every parallel build must bump is a rule-#3 violation surfacing under fan-out."*

It read the registry tests directly before deciding the merge strategy, then laid out a clean four-part resolution: (1) the PM backfills all 6 INVENTORY rows (green on its own — *"a slugged INVENTORY row with no class is skipped (not drift)"* so the rows stay inert until their classes land); (2) make `calculators_test.rb` **derive** the count from the built classes instead of hard-coding 8 (*"the durable rule-#3 fix"*); (3) strip `#199`'s cross-seam edits back to calculator-only; (4) rebase each backend PR onto the fixed `main` so each goes green. The PM backfill landed as `PR #200` (QA PASS, the new box table rendering live, the ingest correctly skipping the six inert slugs) and merged at `39a1d10`. The derived-count fix — globbing `app/calculators/*.rb`, basename, reject `base`, count — landed as `PR #202` (QA PASS), restoring *"rule-#3 conflict-freedom,"* and merged at `e5cf120`.

**Catch #3 — a namespace collision (`Calculators::Date` shadows stdlib `Date`).** The Date backend (`PR #198`) surfaced that defining `Calculators::Date` shadows Ruby's stdlib `Date`, so it qualified Age's references to `::Date` (`age.rb`, two lines) to keep Age working. The orchestrator flagged this as a backend-agent-def harvest item — *"backend.md: mandate `::Date`/`::Time` qualification."* The later QA gate on `#198` confirmed the edit didn't regress Age: *"the full Age unit+envelope+page+system suite green."*

**Two agent deaths — the #140 socket-close failure.** Mid-coordination, the orchestrator hit the recurring `API Error: The socket connection was closed unexpectedly` and both in-flight fix agents (the `#199` strip and the derived-count fix) died before completing. Per the recovery protocol it checked state before re-dispatching: *"both dead agents committed nothing; their worktrees exist at `main` unchanged ... So both tasks just need redoing."* Re-dispatched into the existing worktrees, both completed cleanly — `#199` stripped to its 3 files, the derived-count fix as `PR #202`. No damage.

**The rebase wave — and a #199 surgery.** With `#200` and `#202` on `main`, the github-agent rebased all six backend PRs so CI would re-run against the backfilled rows + derived count. Five rebased clean; **#199 conflicted** — because the earlier "strip" was a *second* commit reverting the cross-seam edits, and rebase replays the *original* commit (which still adds the INVENTORY row + count bump) first. The orchestrator diagnosed it exactly — *"the strip I did earlier was a second commit reverting the registry edits, but rebase replays the original commit ... first → conflict against main's now-authoritative versions"* — and rewrote `#199`'s branch as a single clean commit on current `main` containing only the 3 calculator files, force-pushing to `57742ca`.

**Six gates, six PASS.** All six rebased backends were gated in parallel, each rendering the new box-table verdict (its first real production use across a build wave). Every one came back **PASS**: CI green with *"REGISTRY DRIFT CLEARED"* post-rebase (the gates even showed the before/after — e.g. Right Triangle's pre-rebase failure `Expected ["right_triangle"] to be empty` now passing), the visual non-UI lane all #87 capture noise, and the DB facet a uniform **N/A** (correct — no pages built yet, so nothing has exercised the calculators; the persistence check re-runs meaningfully once the frontends land). The orchestrator held all six for a single batch confirmation per the never-auto-merge rule. The operator said *"Merge the six,"* and they merged sequentially — `main` at **`3f5f57e`**, **14 calculator classes now live** (8 → 14). *"The backend half of iteration-0006 is done."*
