## Chapter 102 — The two new agent definitions land and get reviewed: "defined ≠ adopted" becomes the through-line (2026-06-14)

The two agent-design issues filed in Chapter 101 — `#160 quality-assurance-agent` and `#163 github-agent` — came back as drafts in this chapter, and the way the operator dispatched them is itself part of the experiment's record. He pasted both issue URLs and set the brief: *"Send these two off as subagents and have the following result: 1. PR open to the best of its ability, if decisions have to be made that are unclear, make the best possible one that is aligned with the intent of each agent's work based on what you know from the issue, but also from `conversations/*` which is a folder that has our literal discussions in it. If scanning it (prefer docs/volumes for compactness) is helpful, delve into the raw text too. 2. that's really it, we'll iterate from the PR, just send it off and ask them to make their best judgement calls. Have a summary and specific call out items in the PR description."*

This is a notable instruction in its own right: the operator pointed the drafting subagents at **the journey itself** — the compact `docs/journey/volumes` and, if needed, the raw `conversations/*` transcripts — as the source for *intent*, not just the issue text. The synthesized narrative and the raw record the historian keeps were being used as design inputs by other agents. The assistant dispatched both in parallel, each pointed at the issue plus the existing agent defs (for house style) plus the journey volumes and raw transcripts, with full latitude to make aligned judgment calls and open a PR carrying a Summary + Decisions made + Call-out items.

**Both PRs landed (#166 QA-agent, #167 github-agent).** The `#160` drafter produced `.claude/agents/quality-assurance-agent.md` as a single 234-line file — a vision-capable, report-only pre-merge gate with three facets behind one verdict: **CI** (absorbing `ci-monitor`'s `bin/ci-watch` + root-cause logic and the #140 death-recovery contract), **Visual** (superseding #93 — reads the screenshot PNGs itself so image tokens stay out of the main thread), and **DB persistence** (incorporating #127's narrow per-PR check, keeping `database-agent` separate). It made and flagged its own decisions: opus + vision, a `BLOCKED` verdict added for inconclusive multi-facet cases, the PR-type branching reusing CLAUDE.md's exact visual-gate taxonomy, and #87/#61 *consumed, not folded* (the def names the capture-non-determinism caveat and derives a `main`-green baseline so it's usable today). The `#163` drafter produced `github-agent.md` and, in the assistant's relay, *"recommends effort/priority since no such labels exist; PM boundary = mechanics vs content; dependabot triage stays separate."*

A small worktree-isolation blip recurred and was caught cleanly: the QA drafter's *"initial Write landed in the main checkout rather than the worktree; I moved it in and confirmed the main repo working tree is clean,"* and the github-agent drafter independently flagged the stray copy. The assistant checked `git status --short .claude/agents/`, found it empty, and named it for what it was: *"no leak — main checkout is clean ... the earlier register→deregister blip was the #160 agent's transient mis-write, already moved into its worktree."*

**The review pass surfaced the chapter's through-line: "defined ≠ adopted."** Asked *"What do we think of the GH agent,"* the assistant read it end to end before opining (*"Let me actually read it before opining"*), praised the craft — *"house style nailed, boundaries crisp, and two genuinely sharp technical calls"* (the `behind_by` rebase-detection that doesn't trust `mergeStateStatus`, and the dedupe pair-nuance that knows a calculator legitimately carries *both* a backend and frontend issue so a dup is a same-title **+** same-layer match) — but located the real issue elsewhere: *"the real question isn't the def's quality, it's adoption."* It named the live overlap: *"the PM def **and** CLAUDE.md still say the PM 'owns GitHub Issues' ... two agents claim issue creation ... merging this def **changes nothing operationally** — it's latent until CLAUDE.md routes issue/PR work through it. That rewiring is the actual decision."* And it questioned one capability specifically — *"Centralized PR creation is the questionable capability ... an extra hop per PR for the benefit of consistent labeling"* — recommending the clear wins (dedupe/label/rebase/summary) be adopted and PR-creation held.

The operator acted on that: he had the assistant **pare github-agent down to issues + rebasing only**, deferring PR creation — pushed as commit `2948fac` to PR #167. On re-review of the pared version the assistant called the cut *"the right call ... Tight, coherent scope ... the 'Deferred — PR creation' note is explicit so it reads as a deliberate decision, not a gap."*

**The QA agent drew the same "defined ≠ adopted" diagnosis, plus a substantive design soft-spot.** The operator asked for a deterministic result **table**; the assistant strongly agreed (*"a deterministic, same-shape-every-run result so a glance tells you the gate outcome"*) and sketched the fixed columns. On whether the QA agent would trigger as reliably as `ci-monitor`, it was blunt: *"Honestly — no, not just by existing. This is the same lesson as github-agent: defined ≠ adopted. ci-monitor's dialed-in invocation rate isn't intrinsic — it's manufactured by CLAUDE.md's forceful, repeated, no-exceptions contract language ... The CLAUDE.md rewiring IS the thing that turns the QA agent on — it's the load-bearing change, not the agent file."* And it named the QA agent's real weak point — the **DB-persistence facet is opportunistic, not a reliable gate**: *"Its prerequisite is a populated dev DB ... At pre-merge time that's usually not true, so in practice the DB facet will frequently report `N/A — dev DB not populated`."* The structural reason it can't be fixed in place: *"a true persistence gate would have the agent exercise the calculator (POST a calculation, then verify the row) — but that's a write, which the report-only boundary forbids."* Its recommendation: *"DB-persistence probably belongs in CI as an integration/system test ... rehome #127 as a test convention and drop it from QA."* It also flagged that the QA agent owning vision means *"You won't see the screenshots"* unless it posts them to the PR — a human-visibility cost worth designing around.

**Agent/doc-driven? ✅** — both new responsibilities were authored as agent *definitions* (by drafting subagents mining the issue + the journey + raw transcripts), reviewed against house style and boundaries, and the one capability the assistant questioned (centralized PR creation) was *pared out of the definition* on the operator's instruction rather than worked around in code. No app code changed. The chapter's recurring lesson — that a merged definition is *latent* until the contract routes work through it — is the experiment turning its "fix the agent, not the code" loop onto its own orchestration layer.
