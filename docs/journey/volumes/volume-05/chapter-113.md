## Chapter 113 — The frontend fan-out: a pre-scaffold probe that found a deeper coupling, a midnight-boundary flake, and six pages all PASS (2026-06-15)

The backend half of iteration-0006 closed Chapter 112 with 14 calculator classes live and the orchestrator deliberately *not* repeating the registry scramble: before launching the six frontends, it dispatched an Explore agent to map the frontend "add-a-calculator" file surface — which files are per-calc (safe to fan out in parallel) versus shared (a six-way collision waiting to happen). This chapter is the frontend wave that followed — and it is, again, a chapter about the experiment surfacing real coupling gaps *before* they shipped.

**The map: conflict-free vs. shared.** The Explore agent came back with a clean split. Conflict-free (per-calc, add-only): the page (`<slug>.html.erb`), the result partial (`results/_<slug>.html.erb`), the helper module (`helpers/calculators/<slug>_helper.rb`), the Stimulus controller, and the per-calc tests — rendering is fully convention-based (slug → partial → helper → controller, *"no central dispatcher"*), and the `.stat-grid` component plus the chart libs (`chart.js` + `lightweight-charts`) were already in place, so **no `importmap.rb` edit** was needed. The orchestrator named the two shared collision points: `test/fixtures/calculators.yml` (one row per calc) and `test/helpers/calculators_helper_test.rb` (a hard-coded `helper Calculators::XHelper` line per calc — *"the same hard-coded-registration smell as the backend count"*).

**The pre-scaffold — and the probe built into it.** Learning from the backend's late-discovered registry coupling, the orchestrator decided to pre-scaffold the two shared files centrally first, in one small PR, then fan out conflict-free. But it framed the pre-phase as *also a probe*: *"if making the six calculators 'active' before their pages exist breaks any test (e.g. one that actually visits each active calculator's page), it'll report exactly what rather than papering over it. That tells me whether pre-scaffolding is safe or whether I need a different frontend strategy."* This is the experiment's discipline applied prospectively — spend a probe to learn the coupling rather than discover it by conflict.

**Catch #1 — the derived-helper-includes fix (the clean part).** The pre-scaffold agent solved the harder of the two shared collisions durably: it replaced the eight hard-coded `helper Calculators::XHelper` lines in `calculators_helper_test.rb` with a glob-and-constantize loop —

```ruby
Dir[Rails.root.join("app/helpers/calculators/*_helper.rb")].sort.each do |path|
  helper "Calculators::#{File.basename(path, '.rb').camelize}".constantize
end
```

— mirroring the way `Registry::IngestTest` derives `all_built_rows` from `Dir[app/calculators/*.rb]`. Now each frontend's helper module is auto-included on merge with **no edit to the shared test file** — the rule-#3 conflict-freedom that the backend's derived-count fix (#202) had just established, now applied on the frontend. This shipped as `PR #205`, and the full suite was green (816 runs, 100% coverage line+branch).

**Catch #2 — the probe fired: pre-activating fixtures reddens system-test.** The other half of the pre-scaffold — adding the six active fixture rows — turned out *not* to be safe, and the probe caught exactly why. The QA gate on `#205` (and the pre-scaffold agent re-investigating) found the `system-test` job red: `GET /calculators/compound_interest → ActionView::MissingTemplate`. The mechanism was a genuine coupling the integration tests masked: `registry_frontend_test` only asserts that a *card* exists per `Calculator.active` — it never visits a page, so the gated `test` job stayed green — but the **real browser** in the system-test flow follows a home-catalog link to a calculator page that doesn't exist yet. The pre-scaffold agent stopped and reported rather than working around it, naming the boundary precisely: *"This is the deeper coupling I was explicitly told to STOP and report rather than work around. The fix is a sequencing/design decision that is not mine to force unilaterally."*

**The decision: fixture-active must be coupled to page-exists.** The orchestrator read the failure correctly — *"pre-activating the fixtures turns the system-test red, because the live browser flow on the signed-in home follows a catalog link to `/calculators/compound_interest`, whose page doesn't exist yet → MissingTemplate"* — and made the call: **slim `#205` to just the derived-helper change** (drop the six fixtures), and have *each frontend carry its own active fixture row alongside its page*, so fixture-active and page-exists land atomically per PR. The slim landed (`fa0f72b`), `#205` re-gated to QA PASS including system-test, and two harvest items were banked: a calculator's test fixture must be **activated with its frontend page, never pre-activated**, and more broadly the gap that a calc goes registry-active on backend merge (home card appears) but its page 500s until the frontend lands — *"consider a generic show-page fallback so the gap degrades gracefully"* (later filed as #214). The operator confirmed the merge — *"Merge those two"* — and `#205` + the historian's `#204` (chapters 110–112) went to `main` at `d4136c2`.

**The fan-out: six frontends, fully conflict-free.** With the derived-helper change merged, the orchestrator launched all six frontends in parallel, each building its page + result partial + helper module + Stimulus controller + its **own active fixture row** (coupled with the page) + per-calc tests. The only remaining shared touch was `calculators.yml` — alphabetical inserts that would mostly auto-merge, with the tail rebased on conflict. The six came back, each on-BLEND and at 100% coverage in isolation, the build agents making the §4 picker choices correctly per calculator shape:

- **Loan (#207)** — `.mode-option` option-list (three multi-word modes), per-mode field gating, `.stat-grid--wide` holding a $431k worst case single-line, amortization table.
- **Mortgage (#210)** — the Amortization charts pattern extended: a Chart.js four-component donut (`assert_donut_drawn`) + a lightweight-charts balance curve (`assert_curve_drawn`), each pixel-asserted at >500 non-transparent canvas pixels, plus a 360-row schedule.
- **Compound Interest (#208)** — a frequency option-list + a growth curve (paints).
- **Standard Deviation (#206)** — a Population|Sample **segmented control** (N=2, short labels — the BMI US|Metric vocabulary), each half annotated with its denominator (÷ n vs ÷ n−1) *in text* so the modes read beyond toggle position (DESIGN §6), `--wide` holding 7-digit unit-less values single-line (the MMR precedent).
- **Right Triangle (#211)** — an option-list picker + a **to-scale, labeled SVG triangle figure** (a 3-4-5 renders as a 3-4-5, with the right-angle marker and the angles labeled).
- **Date (#209)** — option-list modes (two multi-word modes → §4 mandates the list) + an Add/Subtract segmented control within `add_subtract`; notably the agent declined a "Today" quick-fill, reasoning from §4 that both `start_date` and `end_date` are *required primary* dates that carry no "today" meaning.

**Catch #3 — a real shared-main flake at the midnight boundary.** Three separate frontend agents independently reported the same `AgeScreenshotsTest` "Today" failure (`2026-06-14` vs `2026-06-15`). The orchestrator took it seriously precisely *because* the session had crossed from 06-14 to 06-15 mid-flight: *"We did cross from 06-14 → 06-15 mid-session, so a 'Today' assertion breaking at the date boundary is plausible — and if it's real on main, it would redden the system-test job on every frontend PR."* The Mortgage agent confirmed it by reproducing the failure on clean `origin/main` with its changes stashed — so `main`'s system-test had gone red *with no commit*, purely from the clock. The Age fix agent root-caused it exactly: the "Today" quick-fill value comes from the **browser's** clock (`age_controller.js`'s `today()` at click time) while the expected value came from **Ruby's** `Date.current` read on the next line, a later instant — and a headless run crossing midnight between the two reads lands them on adjacent days. The fix (`PR #212`, test-only) made the assertion accept a ±1-day window (`[today.prev_day, today, today.next_day]`) — deterministic on either side of midnight, *"not weakened to a no-op — still proves the button fills today's actual date."* This became a frontend.md harvest item: date-dependent system tests must be boundary-safe.

A correction worth recording: the orchestrator initially *held all six FE gates* fearing the Age flake was blocking CI — then the QA probe on `#206` showed Age was a **local-environment** issue (CI runs UTC-consistent and was green), and the orchestrator reversed itself cleanly: *"I was wrong to hold the gates."* The Age fix stayed in flight as hardening rather than a blocker, and the five remaining gates fired immediately.

**Seven gates, seven PASS — the visual lane finally real.** With the backends' gates having run the *non-UI* baseline-diff lane (no new pixels), the frontend wave is where the QA agent's vision-capable **UI-surface** lane finally exercised the real UI — and every gate viewed and reviewed the new shots against DESIGN.md, citing specific pixels rather than hashes: Std Dev's segmented control on surface-white with the denominator in text; Loan's per-mode field gating; Mortgage's donut painting (green P&I-leading → coral tax → amber ins → HOA, legend dots not colour-alone) and balance curve; Compound Interest's growth curve + donut; Right Triangle's to-scale SVG (and a caught **minor cosmetic** — the SVG edge label clips `",000"` in the extreme large-values figure, banked as polish, not a blocker → later #215); Date's leap-correct result. Every home catalog card was confirmed present. All seven came back **PASS** (the six frontends + the Age fix). The orchestrator presented the batch — *"🎉 All seven gates → PASS"* — and the operator said *"y"*.

**The merge — three trailing fixture conflicts hand-resolved.** Merging `#212` first (test-only, no fixture row), then the six FE PRs sequentially: four merged clean (#212, #206, #207, #208), then `#209` (Date) hit the expected `calculators.yml` conflict — `compound_interest` (now on main) and `date` (the branch) had both been inserted after `bmi`. The orchestrator resolved each by **keeping all rows** (a union — alphabetical-insert collisions, nothing semantic), rebasing and merging #209, then #210 (Mortgage, same pattern with `standard_deviation`), then #211 (Right Triangle, keep all three). `main` landed at `07eb397` — *"14 calculator classes, 14 calculator pages (8 → 14, fully backend + frontend)."* A post-wave verification gate confirmed `main` green and the catalog whole: all 14 cards render, all 6 new pages reachable and on-BLEND, no `MissingTemplate`, no Age flake, all three hand-resolved fixture unions parsing.

**Agent/doc-driven? ✅.** The frontend wave repeated the backend's pattern: the experiment's discipline turned coupling into knowledge before it could ship. A built-in probe surfaced a genuine fixture↔page coupling (caught because the build agent stopped rather than worked around it), driving an atomic fixture-with-page convention; a real midnight-boundary flake on shared `main` was root-caused across the JS↔Ruby clock seam and fixed boundary-safe; the derived-helper-includes change carried rule-#3 conflict-freedom onto the frontend. Six brand-new pages built in parallel, each making its own correct §4 picker and chart decisions, all gated PASS through the now-real visual lane — and the only hand-work was three alphabetical fixture-row unions. The Evaluate phase — where the operator looks at all six himself — is next.
