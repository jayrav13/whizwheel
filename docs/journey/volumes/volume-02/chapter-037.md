## Chapter 37 — "Time for backend agent": a design narrowed itself, the user said "this feels icky," and the scope was reframed (2026-06-13)

After the housekeeping session closed, a fresh session opened on the line the experiment had been circling for chapters: *"We ready for the backend or what?!? Haha, time for backend agent."* The frontier — issue #6, the agent that builds the actual calculator math, the heart of the convergence test — was finally going to be crossed. The assistant treated building a brand-new agent definition as design work worth shaping deliberately, pulling up the brainstorming skill (the same gate that produced the PM and frontend agents) before writing anything: *"Building an agent definition from scratch is exactly the kind of creative/design work I shouldn't just wing."*

**The reconnaissance found three genuinely-open decisions, not one `.md` file.** Reading the docs and the sibling agents, the assistant mapped the real state: issue #6 was the mirror of the built `frontend` and `project-manager-agent`; the app foundation existed (auth, RBAC, `Calculation`); but **the calculator layer did not exist at all** — no `app/calculators/`, no `Calculators::Base`, no controller, no route, despite `ARCHITECTURE.md` sketching all of it in prose. Crucially, the spec-artifact format had been *explicitly deferred to this exact moment* — flagged in `ARCHITECTURE.md` *"~3 times as 'TBD, to be settled when the backend agent is built (issue #6).'"* So building the agent meant settling the deferred design too.

**Decision 1 — what a "spec" is.** This is the keystone the whole regeneration-sweep model (Chapter 35) rested on: the agent regenerates code *from the spec*, so the spec is the durable source of truth and the `.rb` is disposable output. The user's answer was *"the GitHub Issue body is the spec"* — no new artifact. The `engineering` issue the PM already authors becomes the single source of truth the backend agent regenerates from, read via `gh issue view` (which works on *closed* issues — necessary, since an issue closes after its first PR merges but the next sweep still regenerates that calculator). The consequence the assistant named: for an issue body to *be* a spec it must carry more than today's `category / source URL / complexity / tags` — it needs **intent, inputs/outputs, and reference values**.

**Decision 2 — where reference values come from** (which decides whether the agent needs web access at all). The user picked, then asked to re-see the options. The assistant laid out three: (1) in the issue body, PM-authored; (2) the agent fetches them from calculator.net itself; (3) hybrid — agent fetches, then pins them into the issue body. It recommended (1), the user's own instinct, and the user confirmed: *"Option 1 - yes, the PM should manage this."* The reasoning that made (1) right is the experiment's signal-cleanliness argument: reference values authored once and frozen in the spec keep *"the regeneration diff … a clean A/B on the *agents* (no calculator.net drift leaking into the signal),"* and they keep the backend agent a pure `Read/Write/Edit/Bash` worker with **no network in its build path**. The string attached — the PM issue template must grow to carry the full spec — was logged as an explicit follow-up to `project-manager-agent.md`, deliberately *not* silently assumed.

**Decision 3 — and the pivot that gives this chapter its name.** With format and reference-values settled, the assistant presented the last architectural fork as scaffolding-vs-worker, and the user picked **Approach B**: `backend.md` as a pure per-calculator fan-out worker, the shared scaffolding (`Base`, the controller, the route, the initializer) carved *out* of the agent. The assistant wrote the full design around it — a tight single-file scribe whose hard write boundary was *"write **only** `app/calculators/<slug>.rb` + `test/calculators/<slug>_test.rb`."*

Then, an hour later, the user read it back and rejected the whole frame:

> "Ugh, wait, this feels icky. This feels like the backend agent's purvue has been constricted quite a bit and value is degrading. Can we explore expanding it? I think the backend agent needs to be able to touch *anything* defined as backend when asked to touch the files needed to be touched to complete the backend"

The user reframed the seam entirely — *"Backend agent is everything that's not frontend - frontend is CSS, templates, JS - the frontend agent is everything client-side of the route, but not including the route"* — and, critically, relocated fan-out safety from *scope* to *isolation*: *"confirming we have things set up to work in worktrees? If that's the case, then we're ok."* The user also drew a line on parameterization: a backend task *"may in itself be parameterized (i.e. build the backend for this calculator), but I think being overly parameterized will hurt us. The backend agent should be able to touch anything that's backend."*

The assistant agreed without hedging — *"honestly it's the right call — scoping the backend agent down to a single-file scribe was draining the value out of it"* — and restated the corrected model: **the seam is the route.** Frontend owns everything client-side of the route; **backend owns everything server-side, route included** (`routes.rb`, controllers, models, migrations, `db/`, `app/calculators/` incl. `Base`, initializers, `lib/`, jobs, rake tasks). *"If it's behind the route, it's the backend agent's responsibility — full stop … it's an engineer, not a file-typist."* Fan-out safety *"stops being about amputating scope and becomes about isolation"* — N agents in N worktrees can all touch `Base` or `routes.rb` and merge later. The assistant verified worktrees were actually available (git 2.50.1; both the `Agent` tool's `isolation:"worktree"` and manual `EnterWorktree`/`git worktree add`) before banking on the reframe, and noted the bonus: it *"un-sticks the earlier 'agent owns the scaffolding but mustn't touch it in a sweep' contortion — gone entirely."*

**Agent-driven?** This chapter is pure design dialogue — no artifact landed in it yet — but it's the most consequential design conversation since Chapter 35, and it shows the experiment's catch-and-refine rhythm at full strength: a design that the brainstorming process had logically narrowed (Approach B *was* the cleanest boundary by the rule the assistant proposed) was reversed by the user on a *value* judgment the process missed — that a maximally-clean boundary had hollowed out the agent. The settled model — **backend = everything server-side of the route, isolated by worktrees rather than by narrowed scope** — is the inverse of where the brainstorm had landed an hour earlier, and the user got there by trusting "this feels icky" over the tidy logic on the page.
