## Chapter 28 — The dependabot-agent: a new report-only agent, dogfooded before it was trusted (2026-06-13)

In the same breath as the screenshot-gate ask, the user opened the session's largest new thread: *"look at the PR list - we have some dependabot PRs. Let's come up with a plan on how we address those as they come. Maybe they're honestly a subagent? Keeps that (a tiny detail, really) out of current context and we have specific rules on things that must be true in order to merge. Thoughts?"*

The assistant agreed the chore fit the mold exactly — *"recurring, self-contained, context-isolatable, and *report-shaped* — the same mold as `ci-monitor`"* — and proposed `dependabot-agent` (Bash + WebFetch, **report-only**). Per PR it would: verify it's Dependabot-authored and bump-only; check CI via `bin/ci-watch`; classify the bump (patch/minor/major) **and blast radius** (CI/GitHub Action vs dev/test gem vs runtime/app gem); read the changelog; and emit a per-PR verdict — **GREEN-LANE** (green + patch/minor + low blast radius) or **NEEDS-HUMAN** (any major, any runtime/app gem, or red CI). On the one real policy choice — auto-merge vs human-gated — the assistant honored the standing invariant and recommended **(a) human-gated** now (the agent *"does all the legwork; you merge `GREEN-LANE` ones with a single glance. Invariant fully intact"*), with a narrow auto-lane **(b)** as a possible codified future opt-in *"once we've watched the classifier be right a few times."* The user accepted policy (a); the agent was built (`280987e`), wired into a new **"Dependency updates"** section of CLAUDE.md, and tracked as issue #18 → PR #19.

The defining move came next. Rather than trust the agent on description alone, the assistant proposed a **single-PR dogfood before merging its own def** — and the user backed the test-run idea. The assistant picked **#3 (`image_processing` 1.14→2.0)** deliberately, as *"the richest test: a *runtime* gem (exercises the blast-radius rule, not just semver), a real *major* with an actual changelog to fetch."* It dispatched the agent (read-and-adopt from the branch def, since the type isn't registered) against #3 only.

The dogfood was *"more useful than a dry run, because it caught a real landmine."* The assistant independently confirmed the agent's headline claim (#3's CI *is* red) and validated the diagnosis: `image_processing` 2.0 makes `mini_magick`/`ruby-vips` **soft** dependencies, so the processor gem drops out of the lockfile and **Active Storage variant processing breaks**:

> "So merging #3 blind would have broken the build — and we get **zero benefit** from it (no image features exist yet). The agent earned its keep on its first run."

And the experiment's core move fired: the dogfood surfaced a def improvement (the agent flagged that `--log-failed` greps are noisy for pinpointing the failing test), so the assistant **fixed the agent definition** — pointing it at the full job log — *"rather than working around it"* (`5b31a11`), folded in before #19 even merged. *"The loop working on itself, visibly."* PR #19 went green (re-watched after the amendment) and, on the user's nod, merged (`e942af0`).

**Agent-driven?** ✅ entirely — a new durable agent definition + a CLAUDE.md section, with the merge rules encoded once. The standout is the *validate-before-trust* discipline applied to a brand-new agent: it was run against a real PR, its accuracy independently checked, and its first self-flagged weakness folded back into the def before it was trusted in production. The same shape as every prior agent's introduction (the historian journaling its own origin; ci-monitor proven before adoption).
