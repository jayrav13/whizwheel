## Chapter 30 — Auto-rebase: the agent's one write-action, and the line between rebase and merge (2026-06-13)

Before journaling, the user pressed on the natural next step and drew a careful distinction: *"Do we rebase on main and push to review the update post-rebase? Do we ask the dependabot-agent to do this autonomously when we know one of these PRs is behind, which I think is safe compared to an auto merge?"*

The assistant agreed the instinct was right and separated three things. The **mechanic**: not a manual `git rebase` (which fights Dependabot over its own branch + lockfile) but the native trigger — *"comment `@dependabot rebase`"* — which rebases the branch onto current `main`, re-resolves the dependency, force-pushes, and re-runs CI. The **caveat**: rebasing *"only fixes the *signal*, not the verdict"* — all three are majors, so they stay NEEDS-HUMAN regardless of CI color; and #3 carried a specific trap — after rebase it *"might actually go **green** — because *no test exercises Active Storage variants*, so the dropped `ruby-vips` never triggers its `LoadError` in CI. That green would be a **false all-clear** hiding a latent runtime landmine."* And the **autonomy question**, where the assistant endorsed the user's line with a table contrasting auto-merge (touches `main`, hard to reverse, worst case a broken `main`) against auto-rebase (touches only the PR branch, trivially reversible, worst case a fresh still-gated CI run):

> "give `dependabot-agent` exactly **one** autonomous write-action — *if a PR is behind its base, post `@dependabot rebase`* — and nothing else. Triage stays report-only; **merge stays human-gated**."

The user approved: *"codify the dependabot-agent update to use @dependabot rebase and then trigger on all 3."* Codifying it produced *another* dogfood finding. The assistant checked which PRs were actually behind and discovered `mergeStateStatus` reports **CLEAN/UNSTABLE but never `BEHIND`** here — because GitHub only flags `BEHIND` when *"require branches up to date"* branch protection is enabled, which this repo lacks. So the def's draft "check for `BEHIND`" guidance was unreliable. The fix: use `compare → behind_by`, which showed all three genuinely behind (by **13 / 62 / 62**) — and that fix was folded into the def (`d7076b4`). `@dependabot rebase` was posted on all three; the codification PR **#20** (with the `behind_by` fix included) merged green on the user's nod (`9d24ea2`).

**Agent-driven?** ✅ — the new capability is a def edit + a CLAUDE.md update, and it gained the agent its *one* write-action with a tightly-scoped rule (only when behind, never on a current PR, never any other action). The chapter is also the second consecutive dogfood that *improved the def while exercising it*: building the auto-rebase trigger exposed that the obvious "behind" signal (`mergeStateStatus`) is silently unreliable without a branch-protection setting the repo doesn't have, and the def was corrected to the reliable `behind_by` comparison before it was trusted.
