## Chapter 35 — The prime directive gets teeth: the full-sweep, regenerate-from-spec iteration model (2026-06-13)

This is the session's load-bearing decision — a methodology change settled *before* the first calculator, that redefines what an "iteration" even is and turns the experiment's central rule from a guideline into something the build process physically enforces. The user opened it as a genuine quandary, framed against the project's premise:

> "the premise of this project is to essentiallly build a calculator via agents, watch for results, iterate on agents. Does the current approach actually have the agents go backwards to previously build calculators per iteration to update them based on decisions too? Or are new calculators built in a bubble using new agent prompts?"

The user sketched the model they wanted — *"agent 2 builds calculator 2 + updates calculator 1 based on its new system prompt … agent 3 builds calculator 3 + updates calculator 1 + 2"* — so that *"git commit is what maps agent to calculator,"* and named the alternative (build new, leave old alone) as *"the less desirable approach."*

**The factual answer: today it's the bubble model.** The assistant checked the actual artifact rather than recalling it, quoting `pm.md`: *"An iteration is the rebuild of `n` **sequentially-next** calculators … using a frozen, committed agent set (pinned to a SHA)."* It confirmed the user read it right — *"There is **no** mechanism that sends a new agent back over calculators 1…N-1. So calculator 1 would be frozen at agent-1 quality forever."*

**The stronger argument was methodological, not product.** The assistant agreed the user's retroactive model was correct but reframed *why*: *"A retroactive rebuild turns every old calculator into a controlled A/B test of the agent."* In the bubble model you compare different calculators built by different agents — *"you can't separate 'agent got better' from 'calc-5 was just easier.' The signal is confounded."* In the retroactive model, `git diff calc-1@agent1 … calc-1@agent3` is *"the **same calculator, only the agent varied**. That diff *is* the measurement."* So the rebuild *"isn't overhead on top of the experiment — it *is* the experiment's instrument."*

**The assistant's one hesitation — and the user's push that overrode it.** The assistant initially proposed a *bounded* benchmark cohort (a small fixed set rebuilt every iteration, the long tail getting cheaper refresh passes) to dodge an *"O(N²)"* review cliff. The user pushed back and won the point:

> "I actually think we *should* sweep all calculators to use the latest agents to refactor. The way we do this is to enqueue many frontend or backend agents to update one calculator each. This fan-out approach I think turns the FE and BE agents into parameterized agents that we can fan out, maybe even using dynamic workflows, to make major updates across the app"

The assistant conceded — *"You've convinced me — and I think the reason you're right is stronger than the convenience argument"* — and articulated the deeper reason in words that became the new rule #1:

> "**The full sweep is the forcing function that makes 'agent-first, never hand-edit code' actually true instead of aspirational.** … If every iteration can blow away and regenerate every calculator from spec + the current agent, then **any fix that lives only in the code gets erased on the next sweep.** That's not a bug — it's the enforcement mechanism."

It also surfaced the one new artifact the model *demands*: the agent must regenerate **from a spec, not from the old code** — otherwise *"calc-1@agent3 is a derivative of agent-1's code … you've re-anchored to the old implementation and lost the clean A/B."* So **specs become first-class**: *"spec + agent + tests are the inputs; the calculator code is a reproducible output."* It noted append-only is preserved by git history, not by freezing the tree (*"In-place regeneration ≠ deletion"*), and that the one cost fan-out *doesn't* erase is total compute — but human review cost *"scales with the **blast radius of the agent change**, not with N"* because the deterministic visual gate passes byte-identical renders for free.

**Encode first, then journal.** The user blocked the historian until the decision was actually landed: *"Well, we need to refine the PM for this and document it someplace, no? What changes are required before we fire off the historian?"* The assistant agreed this was the premise itself — *"journaling a decision that isn't encoded anywhere would violate the whole premise. The historian records what *landed*, not what we *said*. So we encode first, then journal."* It read the real artifacts and produced a precise file-and-owner change set, splitting **methodology (encode now)** from **implementation (deferred to #6)**. The user made two calls: **principles only** (the concrete spec format stays open until #6, to avoid *"over-documenting a methodology *before building a single calculator*"*), and **honor the lane** — the main thread edits `pm.md` + `CLAUDE.md` (agents can't edit their own def / the rulebook), then dispatches the **pm agent** to write the `docs/` half (sole writer of `docs/`).

**What landed.** On a branch:
- `CLAUDE.md` rule #1 rewritten so agent-first is **self-enforcing via the sweep** — *"every iteration rebuilds *all* prior calculators from their specs with the latest agents (a fan-out, one agent per calculator), so any fix living only in calculator code is erased."* (`c8e08de`, `feat(agents): redefine an iteration as a full regenerate-from-spec sweep`).
- `.claude/agents/pm.md` — the iteration redefined from "rebuild of `n` sequentially-next calculators" to *build the next `n` new **and** regenerate every prior calculator with the pinned agent set via fan-out, with the regeneration diff as the iteration's headline evidence.
- The pm agent, dispatched on the branch, wrote the `docs/` half (`62e03ef`): rewrote `INDEX.md`'s iteration concept, added a **Spec** term to `ARCHITECTURE §0` and a new **§3.1 build model** section — *"principles only, spec format flagged TBD-until-#6."*
