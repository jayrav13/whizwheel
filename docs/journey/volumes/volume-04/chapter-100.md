## Chapter 100 — The backfill workflow made contractual: build-time columns the scrape can't derive (2026-06-14)

The operator caught a gap that would otherwise have shipped as tribal knowledge: *"For directive 1, the descriptions are only there for the completed calculators. So, how will the backfill for it work from there? When we backfill newly created (or when they're created), writing them to inventory.md will introduce a description?"*

The assistant's answer named a property of the catalog that hadn't been written down: **`Description` and `Slug` are not scrape-derivable — they're authored at build time.** *"INVENTORY's rows come from the PM's idempotent calculator.net scrape ... but calculator.net has no 'our card blurb' and no notion of our routing slug. So `Description` and `Slug` are **not scrape-derivable** — they're things *we* author when *we* build a calculator. A blank `Description`/`Slug` literally means 'catalogued but not built by us yet.'"* The owner is the PM, not the build agents — *"Build agents must NOT write it — `backend`/`frontend` are scoped away from `docs/`, and a shared INVENTORY edit per build would reintroduce the exact fan-out merge conflict #107 exists to kill."* The natural home already existed in the lifecycle: the iteration **Close** phase, where the PM updates INVENTORY. The cleanest authoring point, the assistant proposed, is the calculator's `spec:v1` issue body: *"the blurb to be authored once, in the calculator's spec ... and the PM transcribes it into INVENTORY at close. That keeps a single authoring point at calculator-definition time rather than the PM inventing copy later."* And two safeguards were already half-built: the columns sit in the preserved-across-refreshes set (a scrape won't clobber them), and because the ingest reconciles against `Base.lookup`, *"it can warn when a built calculator class has no INVENTORY `Slug`/`Description` — so a forgotten backfill surfaces loudly instead of silently shipping a blank card."*

The assistant flagged the gap explicitly — *"None of this is *codified* yet — right now it's just understood. To make it durable ('fix the agent')"* — and the operator authorized it: *"Fold into 153 and queue PM."* The PM rewrote issue **#153** to add a `## Backfill workflow (Slug + Description)` section, a PM-ownership line, and a drift-detection acceptance checkbox. It correctly stopped at its write boundary on the rest — the `spec:v1` template lives in `docs/ARCHITECTURE.md §3.2` (a build-convention doc outside the PM's remit) and the close-phase step belongs in the PM's *own* definition (which it cannot edit) — and reported both with exact locations and proposed text rather than crossing the line. (Its issue edit drew the session's third self-flagged false-positive security warning; the assistant overruled it: *"the security flag is a false alarm — you authorized the #153 edit."* But it still verified the full-body rewrite preserved the design + the #107/#122/#124 dependents before letting backend read #153 as its spec.)

The assistant then took the out-of-PM-remit edits in the main thread, landing **PR #161** (`Part of #153`): `ARCHITECTURE.md §3.2` gained a `Card description` field in the `spec:v1` template plus a section-contract bullet (blurb authored once at definition time), and `project-manager-agent.md` got its table schema corrected to 8 columns, `Slug`/`Description` documented as build-time + preserved-on-refresh, and a **Close-an-iteration** step requiring the PM to author `Slug` + `Description` for each shipped calculator. *"That makes the whole backfill workflow contractual (issue side in #153, doc/agent side in #161) — no longer tribal knowledge."* PR #161 cleared CI green and the operator merged it (`b48f8b3`). **Agent/doc-driven? ✅** — a real workflow gap the operator surfaced by interrogating the data was closed by writing the rule into three durable layers (the issue spec, the build-convention doc, and the PM agent definition) and by building the drift-warning into the ingest, with the PM honoring its own write boundaries and the main thread taking only the edits outside the PM's lane.
