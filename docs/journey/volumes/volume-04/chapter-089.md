## Chapter 89 — The ci-monitor / agent-death investigation, and the pivot to retries-only (2026-06-14)

The recurring "API Error: socket connection closed unexpectedly" deaths that had dogged the bookkeeping agents finally got a dedicated investigation, at the operator's request: *"I'd like to explore the actual ci-monitor failure, any idea what might be causing it? Quick debugging subagent to give us some ideas?"* The assistant offered a hypothesis (long-lived blocking connections) and dispatched a scoped read-only investigator — which **corrected the hypothesis with evidence.** The two genuine deaths in the session's transcripts were **not** ci-monitors at all but the **historian and PM** (both Opus writing agents), and they died *"within 0.3s of each other, mid model-inference, `error: 'unknown'`, `isApiErrorMessage: true`"* — two unrelated agents dying at the same wall-clock second being *"the fingerprint of an **upstream Anthropic-API/harness connection drop**, not anything `bin/ci-watch` does."* The investigator also found three of the "socket" sightings were **false positives** — the string appeared because the historian was reading transcripts that *quoted* earlier errors. The assistant owned the correction: *"My long-poll theory was wrong as a *cause* but right as *exposure*."* The structural lever the repo *does* control: `bin/ci-watch`'s `gh run watch` has no max timeout, so a `--poll` call blocks for the entire CI run, maximizing the window for a platform drop to land on the monitor silently. The analysis was filed as **#140**.

The fix's design then evolved through dialogue. The operator pushed on whether a script change was even needed: *"can't we just ask the ci-monitor to retry for inconclusive results? Does this have to be baked into the script itself, or can we ask the ci-monitor to do more due diligence? Or was this failure causing the failure to bubble up and abruptly end the agent run?"* The assistant separated the two failure modes precisely: the abrupt API death is *the agent's own brain connection dropping* — *"there's nothing for the agent to 'catch': it's not running anymore"* — recoverable only by external orchestrator re-dispatch; while inconclusive/PENDING results *can* be handled at the agent layer with no script edit, *"which fits 'fix the agent, not the code.'"* It first built a bounded-poll + retry version (`7ac919b`, PR #142). But the operator then redirected to a simpler shape — retries only, and *always* use the monitor: the assistant restated the goal as *"ci-monitor.md = **retries, NO bounded-poll/give-up**, and the main thread **always uses ci-monitor**"* (dropping the direct `gh pr checks` glances it had used as a stopgap during the deaths). Because the bounded-poll and retries were in the same file, the assistant **edited #142 directly** rather than split it: stripped the bounded-poll/deadline, kept the retries, restored watch-to-terminal, retitled the PR (`22478ad`). It merged at `849e176`, and since it's on `main`, *"every future `ci-monitor` dispatch uses it — 'always use ci-monitor' restored."* **Agent/doc-driven? ✅** — a misattributed recurring failure was investigated to its real (platform) root cause, the repo-controllable exposure was identified, and the chosen fix lived entirely in the agent definition, refined twice by operator direction.
